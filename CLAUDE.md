# mail_backup — резервное копирование, перенос и восстановление почты по IMAP

Веб-сервис на FastAPI поверх `imapsync`: бэкап почтовых ящиков на отдельный диск
сервера, восстановление из бэкапа, прямой перенос между хостерами, графики.

## Правила работы над проектом

- **Все комментарии и docstring в коде — на русском.**
- **Всё о проекте (решения, архитектура, статус этапов) фиксировать в этом файле.**
- Python в venv, установка прямо в систему (без Docker).
- Вся работа ведётся через git в ветке `main`, отдельных веток под задачи не заводить.
  Коммитить, сливать и отправлять на GitHub — **только по команде пользователя**;
  сообщения коммитов — осмысленные, на русском.
  Секреты, `.env`, `var/` и `.venv/` в репозиторий не попадают (см. `.gitignore`).

## Требования и принятые решения

| Тема | Решение |
|---|---|
| Сервер | Ubuntu 26.04, прямая установка, Python ≥ 3.12 в venv |
| Стек | FastAPI + SQLAlchemy 2 + SQLite (WAL), Jinja2 + HTMX + Chart.js |
| Ящики | ~10 штук |
| Хостеры | Яндекс, Mail.ru, любой IMAP вручную (пресет `custom`) |
| Движок | `imapsync` **2.314** (из GitHub по тегу `imapsync-2.314`, в репозиториях Ubuntu его нет) |
| Хранилище | Локальный Dovecot, Maildir на **отдельном диске** (`MB_BACKUP_ROOT`) |
| Снимки и выгрузка | **restic**: локальный репозиторий на том же диске + копии на другие серверы (SFTP) |
| Админка | Один администратор, логин + argon2-хеш в таблице `settings`; первый вход по одноразовой ссылке |
| Веб | FastAPI + Jinja2 + htmx 2.0.4 (лежит в static, без CDN), свой CSS (светлая/тёмная тема) |
| Доступ к панели | nginx, HTTPS по IP с самоподписанным сертификатом; uvicorn только на 127.0.0.1:8080 |
| Уведомления | Не нужны |
| Срок хранения | Вариант «Б»: снимки restic старше `retention_days` удаляются (0 = бессрочно) |

### Все настройки — через веб-панель (жёсткое требование)

Админ управляет всем из браузера; CLI — только для установки, диагностики
и восстановления доступа. Изменяемые настройки хранятся в БД, а не в env-файле.

| Через веб (хранится в БД) | Только в env-файле (задаёт установщик) |
|---|---|
| Ящики: добавление, правка, удаление, вкл/выкл, проверка подключения | `MB_DATA_DIR` — где лежит сама БД |
| Расписание, срок хранения, исключаемые папки — по каждому ящику | `MB_BACKUP_ROOT` — путь зашит в конфиг Dovecot |
| Запуск бэкапа, восстановления, переноса; отмена; логи | `MB_SECRETS_DIR` — ключи нужны до открытия БД |
| restic: удалённые серверы (SFTP), SSH-ключ (генерация, показ публичного), расписание выгрузки | `MB_LOCAL_IMAP_HOST/PORT`, `MB_VIEW_IMAP_HOST` — связаны с конфигом Dovecot |
| Общие: число параллельных задач, хранение логов (дней), часовой пояс | `MB_IMAPSYNC_BIN` |
| Смена логина и пароля админа | |
| Страница «Система»: место на диске, версии imapsync/Dovecot/restic, статус Dovecot, значения env (только чтение) | |

- Env-настройки в вебе видны, но не редактируются: их смена ломает
  Dovecot или расположение данных, это делается переустановкой.
- Первый вход: установщик печатает одноразовую ссылку с токеном, по ней
  админ задаёт логин и пароль в браузере. Без токена страница первичной
  настройки недоступна. `mail-backup set-admin` остаётся для сброса пароля.
- Изменяемые в панели настройки — `mail_backup/app_settings.py` (ключи `app.*` в `settings`):
  `max_parallel_jobs`, `timezone`, `log_retention_days`, `view_allowed_nets`.

### Хостер — только чтение (жёсткое требование)

При бэкапе на хостере **ничего не менять**: не удалять, не перемещать,
не помечать прочитанным. Письма копируются со всеми флагами и датами.

- imapsync меняет host1 только с флагами `--delete1`, `--expunge1`,
  `--delete1emptyfolders` — сборщик команды обязан их отклонять для бэкапа.
- Явно передавать `--noexpunge1`.
- Флаги (`--resyncflags`) и даты (`--syncinternaldates`) переносятся по умолчанию;
  imapsync сохраняет непрочитанные письма непрочитанными.
- imapsync читает host1 через `Peek(1)` (проверено по исходнику) — \Seen не ставится.
- Защита в коде: `mail_backup/imapsync/command.py::check_safe` отказывает в запуске
  при флагах изменения host1, а при восстановлении/переносе — и при флагах удаления на host2.

### Срок хранения (вариант «Б») и restic (этап 6)

- Maildir в Dovecot — **зеркало** ящика: при включённых снимках бэкап идёт с
  `--delete2 --delete2folders`, удалённое на хостере удаляется и из зеркала.
- История — в снимках **restic** (`restic.py`): после каждого настоящего удачного бэкапа
  `restic backup <Maildir ящика> --tag mailbox-<id> --host mail_backup`, затем
  `forget --keep-within <N>d` для этого ящика (N = `retention_days`, 0 — бессрочно).
  `prune` — раз в сутки в обслуживании, а не после каждого бэкапа (он тяжёлый и берёт
  эксклюзивную блокировку). `--keep-within` считается от самого нового снимка — последний
  снимок ящика не удаляется никогда.
- **Выключатель снимков** (`ResticSettings.enabled`, страница «Снимки»). Выключено — нет
  снимков, очистки и выгрузки, и **зеркало не удаляет** удалённое на хостере (`Job.mirror_deletions`),
  иначе без истории письма пропадали бы насовсем. Удаления в зеркале — только если снимки
  включены **и** restic готов (`jobs.snapshots_wanted`: бинарник, пароль, `repo/config`).
  Существующие снимки при выключении остаются, восстанавливать из них можно.
- Если у ящика ещё нет снимков, а зеркало не пустое — снимок делается **до** imapsync
  (письма, накопленные в зеркале при выключенных снимках). Не удался — этот бэкап идёт без удалений.
- Снимок не удался — бэкап остаётся удачным, ошибка в `Run.snapshot_error`, на обзоре
  состояние «нет снимка».
- Пароль репозиториев — `MB_SECRETS_DIR/restic.pass` (создаёт `ensure_keys`), один для
  локального и удалённых; в панели — только по кнопке «Показать пароль» (POST).
- Блокировки: restic сам (`--retry-lock 3h`); чтение списка снимков — `--no-lock`.
- Восстановление из снимка: `restic restore <id>:<путь> --target Maildir/_restore_<run.id>`,
  временная учётка Dovecot `_restore_<id>` (пароль в `Run.snapshot_password_enc`, учётки
  собирает `dovecot.sync_users` из активных запусков), imapsync читает её как обычный бэкап;
  после запуска каталог и учётка удаляются, воркер при старте подчищает остатки.
  Логины ящиков с «_» в начале запрещены. Перед распаковкой — проверка места (размер × 1.1).
- Выгрузка (`ResticRemote`, `restic_tasks.py`): SFTP `sftp://user@host:port/path`, ssh только
  с ключом `MB_DATA_DIR/ssh/id_ed25519` и своим `known_hosts` (`accept-new`: ключ сервера
  запоминается при первом подключении), `BatchMode`. Удалённый репозиторий создаётся при первой
  выгрузке `init --from-repo … --copy-chunker-params` (дедупликация как в локальном), затем
  `copy`, тот же срок хранения (`forget`) и `prune`.
- SSH-ключ и known_hosts — в `MB_DATA_DIR/ssh`, а не в `/etc/mail_backup`: ключ создаётся
  из панели, а у сервисов `ProtectSystem=full` (/etc только на чтение).
- Задачи restic (`ResticTask`: очистка, выгрузка, проверка) — воркер выполняет **по одной**
  в отдельном потоке, вне лимита запусков imapsync; ставит их расписание «Обслуживание»
  (`ResticSettings.schedule`, по умолчанию 05:00) или кнопки. Отмена — как у запусков (SIGTERM группе).
- «Репозитория нет» — `restic.is_no_repo`: restic ≥ 0.17 отвечает кодом 10, а 0.16 (Ubuntu 24.04,
  минимальная версия в install.sh) — кодом 1 с текстом «unable to open config file … no such
  file or directory / does not exist». Учитывать обе формы.
- Тесты по умолчанию считают restic не установленным (`MB_RESTIC_BIN` в conftest), тест с
  настоящим restic задаёт бинарник сам; в CI он идёт с restic 0.16 из apt.
- Проверено с настоящим restic 0.18.1 на Mac (снимок, восстановление, init удалённого,
  copy, check); SFTP вживую не проверялся.

### Просмотр бэкапа почтовым клиентом (только чтение)

- У ящика по кнопке на его странице заводится вторая учётка Dovecot `_view.<local_login>`
  (`Mailbox.view_password_enc`, None — выключено; пароль — по кнопке «Показать пароль», POST).
  Домашний каталог — Maildir ящика (поле home в passwd-file), `userdb_acl_groups=mb-view`.
- ACL (`acl = vfile`): `owner` — все права (явно, иначе при глобальных записях владелец может
  остаться без прав), `group-override=mb-view` — только `lr`. 2.3 — файл
  `deploy/dovecot/mail_backup.acl` → `/etc/dovecot/mail_backup.acl`, 2.4 — в самом конфиге.
  В шаблоне 2.4 убран `mail_home`: домашний каталог даёт userdb (`home:default`).
- Сеть: Dovecot слушает `127.0.0.1` и IP из `install.sh --imap-listen` (`MB_VIEW_IMAP_HOST`,
  пусто — только локально; доступ пользователя — по VPN на обычный IP сервера). Порт 143 без TLS.
  Учётки imapsync и восстановления — `allow_nets=127.0.0.1/32`; учётки просмотра — ещё и сети
  из панели (`app.view_allowed_nets`, «Настройки»). Только IPv4: «:» — разделитель passwd-file.
- Не проверено вживую (Dovecot на Mac нет) — чек-лист в INSTALL.md; в первую очередь — что
  бэкапы после включения ACL работают и что создать папку учёткой просмотра нельзя.

## Архитектура

```
хостер ──imapsync──▶ локальный Dovecot (Maildir на отдельном диске)   = бэкап
локальный Dovecot ──imapsync──▶ любой ящик                            = восстановление
хостер A ──imapsync──▶ хостер B                                       = перенос
```

- Для каждого ящика в локальном Dovecot заводится своя учётка
  (`Mailbox.local_login` / `local_password_enc`). Dovecot слушает 127.0.0.1:143 (и IP просмотра, если задан).
- Веб (uvicorn) и воркер — два systemd-сервиса, общая SQLite в режиме WAL.
- Пароли ящиков в БД шифруются Fernet; ключи — в `MB_SECRETS_DIR` (права 600).
- В imapsync пароли передаются через `--passfile1/--passfile2`, не в командной строке.
- Статистика каждого запуска (письма, байты, ошибки, размеры ящиков) пишется
  в таблицу `runs` и служит источником для графиков.

## Настройки (переменные окружения)

Сервер: `/etc/mail_backup/mail_backup.env`; разработка: `.env` в корне проекта
(см. `.env.example`). `.env` ищется по абсолютному пути от корня проекта, а не от
текущего каталога — CLI на сервере запускается через `sudo -u mailbackup` откуда угодно.

## Деплой и проверка

Пользователь деплоит на свой хост и тестирует **поэтапно**; после каждого этапа
всё сливается в `main`. Установка и обновление — `deploy/install.sh`, инструкция
и чек-лист проверки — `deploy/INSTALL.md`. **Каждый этап, которому нужно что-то
на сервере (пакеты, systemd-юниты, nginx, restic), дополняет install.sh и INSTALL.md.**

Два окружения:
- **DEV** — тестовый сервер, отдельного диска нет, бэкапы на системном диске.
- **PROD** — бэкапы на отдельном диске, смонтированном в `MB_BACKUP_ROOT`. Тройная защита
  от записи мимо диска: установщик требует точку монтирования; Dovecot получает
  `RequiresMountsFor`; `jobs.check_backup_storage()` перед каждым бэкапом/восстановлением.
- Режим и путь к бэкапам фиксируются в env-файле при первой установке; повторный
  запуск установщика с другими значениями отклоняется.

Доставка кода — **только через git**: `/opt/mail_backup` — git-клон, владелец —
SSH-пользователь (не root); `git clone`/`git pull` без sudo (ключ к репозиторию у этого
пользователя), установщик — через sudo. Установщик работает из каталога, где лежит.

Установщик проверен только `bash -n` и shellcheck (правки этапа 6 — только `bash -n`) — живого прогона на 26.04 ещё не было.
imapsync ставится по тегу с проверкой SHA256 (константа в install.sh — обновлять вместе с версией). Пути на сервере: код `/opt/mail_backup`,
данные `/var/lib/mail_backup`, бэкапы `/srv/mail_backup`, секреты `/etc/mail_backup`,
пользователь сервиса `mailbackup`.

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `MB_DEPLOY_MODE` | `dev` | `prod` — бэкапы только на смонтированном отдельном диске |
| `MB_DATA_DIR` | `/var/lib/mail_backup` | БД, логи imapsync, tmp |
| `MB_BACKUP_ROOT` | `/srv/mail_backup` | точка монтирования диска с бэкапами |
| `MB_SECRETS_DIR` | `/etc/mail_backup` | `secret.key`, `session.key` |
| `MB_LOCAL_IMAP_HOST/PORT` | `127.0.0.1` / `143` | локальный Dovecot |
| `MB_VIEW_IMAP_HOST` | пусто | IP для просмотра почты клиентом (`install.sh --imap-listen`) |
| `MB_IMAPSYNC_BIN` | `imapsync` | путь к imapsync |
| `MB_RESTIC_BIN` | `restic` | путь к restic |
| `MB_MAX_PARALLEL_JOBS` | `2` | одновременных запусков imapsync |

## Формат вывода imapsync (сверено с исходником)

- Прогресс: `... ETA: <дата>  <сек> s  <осталось>/<всего> msgs left`.
- Итог: блок `++++ Statistics` (`Transfer time : N sec`, `Messages transferred : N`,
  `Total bytes transferred : N (...)`, ...), строка `Detected N errors`.
- Размеры ящиков `Host1/Host2 Nb messages`, `Total size` печатаются в начале и в конце —
  берём последние значения.
- Коды выхода: 0 — успех, 111 — завершён с ошибками по письмам (статус `warning`),
  остальное — сбой (10 соединение, 12 TLS, 16 авторизация и т.д.).

```

mail-backup backup <id> [--check|--dry|--estimate]  бэкап сейчас (--check: только вход,
                                         --estimate: только размеры папок)
mail-backup dovecot-sync                 пересобрать учётки Dovecot
mail-backup setup-link [--base-url URL]  одноразовая ссылка создания админа
mail-backup worker                       воркер (запускает systemd)
mail-backup restic <аргументы>           restic с локальным репозиторием и паролем приложения
                                         (например: sudo mail-backup restic snapshots)
```

После появления панели `mailbox-add`/`backup` — только для диагностики.

## Оценка места (RunKind.ESTIMATE)

- Кнопка «Оценить» (ящик, список, страница «Место») ставит запуск `estimate`:
  `imapsync --justfoldersizes` — EXAMINE и размеры писем по папкам, ничего не копирует,
  на хостере ничего не меняет. Нужен и host2 (локальный Dovecot) — imapsync всегда
  подключается к обеим сторонам.
- Парсер собирает строки `Host1 folder N/M [имя] Size: … Messages: … Biggest: …`
  в `Run.folder_stats` (JSON); кириллица берётся из формы `[mUTF-7] = [UTF-8]`.
- Страница «Место» берёт по каждому ящику последний удачный запуск с размерами
  (оценка или бэкап) и считает (`storage_estimate.py`):
  зеркало = объём × 1.02 + 2 КиБ на письмо; restic ≈ объём × 0.8;
  рекомендуемый диск = (зеркало + restic) × 1.3. Коэффициенты — константы в модуле.
- На отдельном диске сравнивается его размер, на системном (dev) — свободное место.

## Восстановление и перенос (этап 4б)

- Мастер `/mailboxes/{id}/transfer`: откуда (бэкап в Dovecot — `restore`, или хостер
  напрямую — `migrate`), куда (этот же ящик с сохранённым паролем — только для restore,
  или другой), раскладка (по тем же папкам с `--automap` или всё в одну папку
  `--subfolder2`), затем «Пробный прогон» (`--dry`) или «Запустить сразу».
- После удачного пробного — кнопка «Запустить по-настоящему» (`POST /runs/{id}/repeat`)
  с теми же параметрами; пароль переходит в новый запуск.
- Восстановление без удачного бэкапа не разрешается; перенос в тот же ящик — тоже.
- Получатель не может быть этим сервером (`jobs.is_local_host`: localhost, loopback,
  `MB_LOCAL_IMAP_HOST`) — проверка и в форме, и в `jobs.run_target_endpoint`: запись в
  свой Dovecot испортила бы зеркало.
- Имя папки для `--subfolder2` — только `[A-Za-z0-9 _-]` (`command.SUBFOLDER_RE`):
  imapsync (`sanitize_subfolder`) молча выбрасывает остальное, кириллица дала бы пустое
  имя и письма легли бы в корень. `--subfolder2` сам выключает `--automap`, мы его не передаём.
- В `--dry` imapsync не увеличивает «Messages transferred»; план считается по строкам
  `msg … copying to … (not really since --dry mode)` → `Run.messages_planned`.
- Пароль получателя (`Run.target_password_enc`) стирается после настоящего запуска,
  у пробных — через 24 ч (`jobs.forget_target_passwords`, раз в час в воркере).
  Без пароля мастер открывается заполненным (`?from_run=N`), пароль вводится заново.
- Запуск restore/migrate занимает ящик-источник, как и бэкап: одновременно с его
  бэкапом не идёт.

## Графики (этап 5)

- Страница «Графики» (`/charts?days=7|30|90|365&mailbox=N`) и график за 14 дней на обзоре.
  Данные готовит `stats.collect()`, в страницу — JSON в `<script type="application/json">`,
  рисует `app.js` (Chart.js; встроенные скрипты запрещены CSP). Chart.js подключается
  блоком `{% block scripts %}` только на страницах с графиками.
- В графики идут только настоящие бэкапы; день — дата окончания в поясе админки.
  Размер ящика (`host1_bytes`) берётся и из оценок/пробных бэкапов и тянется вперёд
  до следующего замера (это состояние, а не событие).
- Графики: скопировано за день, размер ящиков (стопка областей), время imapsync за день,
  результаты по статусам, ошибки по письмам; под ними — таблица итогов (она же
  доступная замена графикам). Одна ось Y на график, никаких двух шкал.
- Цвета: 8 цветов `--series-N` в app.css (порядок проверен валидатором на различимость
  при дальтонизме, светлая и тёмная тема). Цвет закреплён за ящиком по порядку добавления
  (`stats.color_slots`), не зависит от фильтра; при > 8 ящиках восьмой — серый «Другие».
- Обзор: состояние бэкапа ящика (`dashboard.backup_health`): в порядке / с ошибками /
  сбой (последний настоящий бэкап не удался) / **просрочен** (по расписанию, а удачного
  бэкапа нет дольше `STALE_AFTER` = 26 ч) / ещё не было / выключен. Плитка «Бэкапы
  в порядке N из M» и блок «Требуют внимания». График обзора — вне блока автообновления.

## Веб-панель и воркер — ключевые решения

- Даты в БД — «наивный UTC» (`models.utcnow()`); в пояс админки — только при выводе.
- Схема БД: `db.create_tables()` создаёт таблицы и **добавляет недостающие колонки**
  (новые колонки обязаны быть nullable или с `server_default`). Сложные миграции — Alembic.
- Безопасность панели: CSRF-токен в сессии (формы — поле `csrf_token`, htmx — заголовок
  `X-CSRF-Token` из `hx-headers` на body); блокировка входа после 5 неудач за 5 минут с IP;
  смена пароля меняет `admin_session_version` → все прочие сессии выходят; `next` после входа —
  только локальные пути; nginx перезаписывает `X-Forwarded-For`.
- Воркер — отдельный процесс, каждый запуск в своём потоке; не больше одного запуска на ящик;
  отмена — флаг `Run.cancel_requested`, воркер шлёт SIGTERM (и SIGCONT — вдруг на паузе) группе
  процессов imapsync; пауза — флаг `Run.pause_requested`, воркер шлёт SIGSTOP/SIGCONT и ставит
  `Run.paused_at` (только в фазе imapsync, не во время снимка/распаковки). Пауза, а не
  «остановить и запустить заново»: повторный запуск снова читает заголовки всех писем — на
  ящике Mail.ru в 20 тыс. писем это 20–30 мин. После долгой паузы хостер рвёт соединение,
  imapsync переподключается сам. Кнопки — макрос `run_controls` (обзор, ящики, запуски,
  страница запуска), возврат на ту же страницу через `next` (`common.safe_next`);
  при старте «зависшие» RUNNING → FAILED; heartbeat в `settings.worker_heartbeat` (панель
  показывает «воркер не отвечает» через 60 с тишины).
- SQLite: `busy_timeout` 30 с, `synchronous=NORMAL` (WAL). Живые поля запуска (PID, прогресс)
  пишет `jobs.save_live`: при «database is locked» значения откладываются до следующей записи,
  запуск не падает (на DEV-сервере первый бэкап 20 ГиБ упал так на 12%). Если воркер перестал
  читать вывод imapsync из-за исключения, `runner._terminate` завершает группу процессов —
  раньше imapsync оставался работать сиротой.
- Расписание: строка «ЧЧ:ММ[, ЧЧ:ММ]» в поясе админки; слоты раньше последней правки ящика
  не срабатывают (новое расписание не запускает «пропущенный» бэкап сразу).
- Логин ящика после создания не меняется (другой логин — другой ящик; зеркало с `--delete2`
  иначе снесло бы бэкап). Удаление ящика в панели не удаляет Maildir на диске.
- Проверено локально: pytest (113 тестов, один — с настоящим restic, если он установлен) + скриншоты страниц в headless Chrome
  (светлая/тёмная тема, ширина 390px). На сервере ещё не запускалось.

## Этапы

1. ✅ **Каркас**: конфиг, БД, модели, шифрование, пресеты, CLI, тесты.
2. ✅ **Обёртка imapsync**: сборка команды (с защитой host1), запуск,
   разбор прогресса и итоговой статистики, учётки Dovecot, шаблон конфига 2.4.
   Не проверено вживую (на Mac нет imapsync/Dovecot) — проверить на сервере.
3. ✅ **Воркер**: очередь, расписание, лимит параллельности, отмена, очистка логов,
   настройки в БД.
4. ✅ **Админка**: первичная настройка по токену, вход, ящики с пресетами хостеров,
   проверка подключения, ручной и пробный запуск, отмена, живой прогресс и лог,
   «Настройки», «Система».
4б. ✅ **Восстановление и перенос из панели**: мастер с выбором получателя, раскладкой
   папок и пробным прогоном. Не проверено вживую — чек-лист в INSTALL.md.
5. ✅ **Графики**: объёмы по дням и ящикам, размер ящиков во времени,
   длительность и ошибки, статус последнего бэкапа («просрочен»), график на обзоре.
   Живой прогресс — с этапа 4. Проверено на демо-данных (скриншоты), не на сервере.
6. ✅ **restic**: снимки после бэкапа (выключаются в панели), срок хранения, копии на другие
   серверы по SFTP, восстановление из снимка на выбранную дату — всё настраивается в вебе.
   Не проверено на сервере (SFTP — вовсе вживую) — чек-лист в INSTALL.md.
7. ⏹ **Деплой**: установщик ставит всё (пакеты, imapsync, Dovecot, сервисы, nginx с
   самоподписанным HTTPS). Этап закрыт в текущем виде (решение от 2026-10-14):
   `--domain` + Let's Encrypt и бэкап самой БД/ключей не делаем.
