# Установка на Ubuntu 26.04

Установку и обновление выполняет `deploy/install.sh`. Повторный запуск безопасен:
ключи, БД, файл настроек и бэкапы он не трогает.

| Что | Где |
|---|---|
| Код и venv | `/opt/mail_backup` (git-клон, владелец — ваш пользователь) |
| Данные (БД, логи, учётки Dovecot) | `/var/lib/mail_backup` |
| Бэкапы | `/srv/mail_backup` (в PROD — отдельный диск) |
| Настройки и ключи | `/etc/mail_backup` |
| Пользователь сервиса | `mailbackup` |
| Команда приложения | `mail-backup` (обёртка в `/usr/local/bin`, сама переключается на `mailbackup`) |

## Код на сервере (git)

Клонировать **от своего пользователя, без sudo**: SSH-ключ к репозиторию лежит у него,
у root ключа нет. Каталог один раз создаётся под своим пользователем (права 755 —
чтобы пользователь сервиса `mailbackup` мог читать код):

```bash
sudo install -d -o "$USER" -g "$USER" -m 0755 /opt/mail_backup
git clone <URL-репозитория> /opt/mail_backup
```

`.venv` и `*.egg-info`, которые установщик создаёт от root, есть в `.gitignore` —
`git pull` их не трогает.

## DEV — тестовый сервер без отдельного диска

```bash
sudo /opt/mail_backup/deploy/install.sh --mode dev
```

Бэкапы лягут в `/srv/mail_backup` на системном диске — установщик предупредит об этом.

## PROD — бэкапы на отдельном диске

Сначала смонтировать диск в `/srv/mail_backup` (пример для нового диска `/dev/sdb`):

```bash
sudo mkfs.ext4 -L mailbackup /dev/sdb          # ВНИМАНИЕ: стирает диск
sudo mkdir -p /srv/mail_backup
echo "UUID=$(sudo blkid -s UUID -o value /dev/sdb) /srv/mail_backup ext4 defaults,noatime 0 2" \
  | sudo tee -a /etc/fstab
sudo mount /srv/mail_backup && findmnt /srv/mail_backup
```

Затем склонировать код (см. выше) и:

```bash
sudo /opt/mail_backup/deploy/install.sh --mode prod
```

Защита от записи бэкапов мимо диска:

- установщик в режиме `prod` прерывается, если `/srv/mail_backup` не точка монтирования;
- Dovecot получает `RequiresMountsFor=/srv/mail_backup` и не стартует без диска;
- приложение перед каждым бэкапом проверяет, что диск смонтирован, иначе запуск — «сбой».

Другой путь к диску: `--backup-root /mnt/backup`. Режим и путь запоминаются
в `/etc/mail_backup/mail_backup.env`; повторный запуск с другими значениями
установщик отклонит, чтобы случайно не переключить PROD в DEV.

## Что делает установщик

1. Проверяет ОС, режим и (в PROD) диск.
2. Ставит пакеты: git, python3-venv, dovecot-imapd, nginx, openssl, Perl-модули для imapsync.
   Пакеты, которых нет в репозиториях, пропускает с предупреждением.
3. Скачивает imapsync 2.314 по тегу с GitHub, сверяет SHA256, проверяет запуск.
4. Создаёт пользователя `mailbackup` и каталоги с нужными правами.
5. Создаёт `/etc/mail_backup/mail_backup.env` (только при первой установке).
6. Ставит приложение в venv, создаёт ключи и БД (`mail-backup init`).
7. Ставит конфиг Dovecot из `deploy/dovecot/dovecot-<2.3|2.4>.conf` по версии
   установленного Dovecot (сначала проверяет `doveconf`; оригинал пакета сохраняется
   как `dovecot.conf.orig-mail_backup`), проверяет, что он слушает только `127.0.0.1:143`
   (и IP просмотра почты из панели, если выбран). Адреса — в `/etc/dovecot/mail_backup_listen.conf`,
   его пишет root-помощник `/usr/local/sbin/mail-backup-dovecot-listen`. Для Dovecot 2.3 кладёт
   `/etc/dovecot/mail_backup.acl`.
8. Ставит и (пере)запускает сервисы `mail-backup-web` (панель на `127.0.0.1:8080`)
   и `mail-backup-worker` (очередь и расписание), включает `mail-backup-dovecot-listen.path` —
   он применяет к Dovecot адрес просмотра почты, когда его меняют в панели.
9. Настраивает nginx: HTTPS на 443 с самоподписанным сертификатом, редирект с 80.
   Если nginx уже стоял с другими сайтами и конфликтует — останавливается, ничего не ломая.
10. Печатает адрес панели и одноразовую ссылку для создания администратора.

## Вход в веб-панель

В конце установки будет ссылка вида `https://<IP>/setup?token=...` — по ней задаются
логин и пароль администратора. Ссылка одноразовая, действует 24 часа. Новая:

```bash
sudo mail-backup setup-link --base-url https://<IP-сервера>
```

Браузер предупредит о самоподписанном сертификате — это ожидаемо, нужно подтвердить.
Адрес в ссылке — первый IP сервера; другой адрес или имя: `install.sh ... --host АДРЕС`.

Если порты 80/443 закрыты или заняты — панель доступна через SSH-туннель:

```bash
ssh -L 8080:127.0.0.1:8080 user@server
# в браузере: http://localhost:8080
```

Забыли пароль: `sudo mail-backup set-admin admin`.

## Просмотр бэкапа почтовым клиентом

Бэкап любого ящика можно открыть в Thunderbird, Apple Mail и т.п. — **только для чтения**
(удалить, переместить, пометить прочитанным нельзя; права режет ACL Dovecot).

1. Панель → «Настройки» → «Просмотр почты»: адрес сервера, доступный из VPN (список — IPv4-адреса
   интерфейсов сервера), и сети, откуда разрешён вход (например, `10.8.0.0/24`). Подсказка там же
   показывает адрес, с которого вы сейчас зашли в панель. Dovecot применяет новый адрес за несколько
   секунд (reload, идущие бэкапы не рвутся) — под полем видно «Dovecot слушает: …» или ошибку.
   Порт 143 без TLS — открывать только для сети VPN (ufw: `sudo ufw allow from <сеть VPN> to any port 143 proto tcp`).
2. Раньше адрес задавался `install.sh --imap-listen` (`MB_VIEW_IMAP_HOST` в env-файле): при
   обновлении он сам переносится в панель, а строка из env-файла убирается.
3. Страница ящика → «Включить просмотр» → «Показать пароль». В клиенте: IMAP, сервер и порт
   со страницы, без шифрования, обычный пароль, логин `_view.<логин ящика>`.

Адрес не выбран («только 127.0.0.1») — через SSH-туннель: `ssh -L 1143:127.0.0.1:143 user@server`, в клиенте `localhost:1143`.

## Обновление

```bash
cd /opt/mail_backup && git pull                         # без sudo
sudo ./deploy/install.sh --mode dev                     # или prod — тот же, что при установке
```

Установщик перезапускает панель и воркер; идущие бэкапы при этом прерываются
(помечаются «сбой: воркер был перезапущен») — лучше обновляться, когда ничего не идёт.

## Проверка этапов 3–4 (панель и воркер)

1. Зайти по ссылке из установщика, создать администратора.
2. «Система»: воркер — «работает», Dovecot — «доступен», imapsync — 2.314.
3. «Ящики» → «Добавить ящик»: выбрать Яндекс или Mail.ru, ввести адрес и **пароль
   приложения**, нажать «Проверить подключение» — должно быть «Вход выполнен успешно».
4. Нажать «Оценить» — через несколько секунд будет число писем, объём по папкам
   и сколько места нужно под бэкап. Итог по всем ящикам — страница «Место».
   Чтобы ящик сначала только оценить, без бэкапа ночью, — снять галочку
   «Бэкап по расписанию включён».
5. На обзоре нажать «▶ Бэкап» — откроется страница запуска с живым
   прогрессом и логом. Дождаться «успешно».
6. Ещё раз «▶ Бэкап» — «Писем перенесено: 0» (всё уже в бэкапе).
7. Проверить «■ Остановить» на идущем запуске и «⏸ Пауза» / «▶ Продолжить»: на паузе
   `ps -o stat= -p <pid>` показывает `T`, после «Продолжить» строки `copied to` в логе идут дальше.
   Пауза дольше ~30 мин: хостер закроет соединение, imapsync должен переподключиться сам.
8. Поставить время запуска на пару минут вперёд — бэкап должен стартовать сам.

На хостере при этом:

- непрочитанные письма **остались непрочитанными**, ничего не удалено и не перемещено.

На сервере:

- письма в хранилище (числа совпадают с хостером, включая непрочитанные):
  `sudo doveadm mailbox status -u user@yandex.ru 'messages unseen' '*'`
- кириллические папки на месте: `sudo doveadm mailbox list -u user@yandex.ru`
- файлов паролей не осталось: `sudo ls /var/lib/mail_backup/tmp/` — пусто.

## Проверка этапа 4б (восстановление и перенос)

Нужен второй, **тестовый** ящик-получатель (например, пустой ящик на Mail.ru)
и ящик-источник, у которого уже есть удачный бэкап.

1. «Ящики» → «Восстановить…» у ящика-источника. В блоке «Откуда» видна дата
   последнего бэкапа и число писем.
2. «Восстановить из бэкапа» → «В другой ящик» → ввести тестовый ящик и пароль приложения →
   «Проверить вход в получатель» — «Вход выполнен успешно».
3. Попробовать имя папки кириллицей при «Всё в отдельную папку» — должна быть ошибка.
   Вписать IMAP-сервер `127.0.0.1` — тоже ошибка (в своё хранилище писать нельзя).
4. «Пробный прогон» → на странице запуска «ничего не скопировано, будет скопировано
   писем: N» (N ≈ числу писем в бэкапе). В тестовом ящике **ничего не появилось**.
5. «▶ Запустить по-настоящему» → дождаться «успешно». В тестовом ящике — те же папки
   (Отправленные/Спам сопоставлены с папками Mail.ru), непрочитанные — непрочитаны.
6. Ещё раз через мастер то же самое — «Писем перенесено: 0» (дублей нет).
7. «Перенести напрямую с хостера» во «Всё в отдельную папку» `From-Yandex` —
   в тестовом ящике появилась папка `From-Yandex` со всей структурой внутри.
8. Через сутки у пробных прогонов пароль получателя стирается: кнопка
   «Запустить по-настоящему» сменяется на «Запустить заново (нужен пароль получателя)».

На источнике (хостере) при этом ничего не меняется; в получателе ничего не удаляется.

## Проверка этапа 5 (графики)

Ничего ставить не нужно: Chart.js 4.4.7 лежит в `mail_backup/web/static/`
(без CDN — CSP пускает скрипты только с самой панели). Достаточно обновиться.

1. «Графики»: пять графиков (скопировано, размер ящиков, время, результаты, ошибки)
   и таблица «Итого за период». Наведение на столбец — подсказка с датой, ящиками и «Всего».
2. Переключить период и ящик — страница обновляется сразу, цвет ящика не меняется.
3. Цифры совпадают со «Запусками»: число бэкапов, объём, ошибки (пробные прогоны,
   восстановления и переносы в графики не входят).
4. Обзор: плитка «Бэкапы в порядке N из M», внизу — график за 14 дней.
5. Выключить у тестового ящика расписание и через сутки включить обратно — на обзоре
   появится «Требуют внимания: просрочен» и метка «⏱ просрочен» в таблице;
   после удачного бэкапа она исчезнет. Сбой последнего бэкапа — метка «сбой».
6. Смена темы системы (светлая/тёмная) перекрашивает графики без перезагрузки.

## Проверка этапа 6 (снимки restic)

Установщик ставит `restic` из репозитория Ubuntu (нужен ≥ 0.16) и создаёт локальный
репозиторий `$MB_BACKUP_ROOT/restic`. Снимки **включены по умолчанию**, выключаются
на странице «Снимки».

1. «Снимки»: restic — версия, репозиторий — путь и размер. «Показать пароль» —
   **сохраните его вне сервера**: без него снимки на удалённых серверах не расшифровать.
2. «▶ Бэкап» у ящика, где бэкап уже был → на странице запуска фаза «создаётся снимок restic…»,
   в итоге «Снимок restic: xxxxxxxx · добавлено …». Первый раз снимков два: до зеркалирования
   (письма, накопленные в зеркале) и после.
3. На сервере: `sudo mail-backup restic snapshots` — снимки с тегом `mailbox-<id>`.
4. Удалить тестовое письмо на хостере → бэкап → «Восстановить…» → «Из снимка на дату» →
   снимок до удаления → «В другой ящик» (тестовый) → пробный прогон, затем настоящий.
   Письмо появилось в тестовом ящике. После запуска `ls /srv/mail_backup/maildir/` —
   каталогов `_restore_*` нет.
5. Выключить снимки → бэкап: в логе imapsync нет `--delete2`, снимок «не делался».
   Включить обратно.
6. Срок хранения ящика 1 день → «Очистить сейчас» → в логе задачи `forget … --keep-within 1d`
   и `prune`. Самый новый снимок остаётся всегда.
7. «Проверить целостность» → задача «успешно» (`no errors were found` в логе).

### Проверка кэша сверки imapsync

1. Первый бэкап после обновления сверяет весь ящик, как раньше (кэш пустой). В логе запуска
   у каждой папки строки `Local cache directory: /var/lib/mail_backup/imapsync_cache/<id>/…`
   и `CACHE h1 h2: 0 files`.
2. Следующий бэкап: `CACHE h1 h2: <N> files`, где N ≈ число писем в папке, и запуск
   в разы короче. В панели: «X / Y сверено», под полосой «скопировано писем: …»,
   без «осталось ≈ 5 дней».
3. `sudo ls /var/lib/mail_backup/imapsync_cache/` — по каталогу на ящик.
4. Страница ящика → «Полная сверка» → каталог ящика исчез; следующий бэкап снова сверяет
   все письма (`CACHE h1 h2: 0 files`).

### Проверка просмотра почты клиентом

1. «Настройки» → «Просмотр почты» → выбрать IP → через несколько секунд «Dovecot слушает: 127.0.0.1, <IP>».
   `ss -ltn | grep :143` — ровно `127.0.0.1:143` и `<IP>:143`; `cat /etc/dovecot/mail_backup_listen.conf`;
   `journalctl -u mail-backup-dovecot-listen -n 20` — запуск помощника. Проверить, что запуск идёт и при
   быстрой повторной смене адреса, и что после смены адреса работающий бэкап не оборвался.
   Вернуть «только 127.0.0.1» — `<IP>:143` пропал. Обновление с `--imap-listen`: адрес перенёсся в
   панель, строки `MB_VIEW_IMAP_HOST` в env-файле нет.
   Dovecot 2.4: `doveconf -n | grep -A2 acl` — записи `owner` и `group-override=mb-view`;
   `doveconf -n | grep listen` — `!include` подхватился.
2. Бэкап ящика после обновления проходит как раньше (учётки imapsync получили `allow_nets=127.0.0.1/32`,
   а владелец — явные права ACL). Если упал с ошибкой входа — `journalctl -u dovecot -n 50`.
3. «Настройки» → сеть VPN; ящик → «Включить просмотр». Подключиться клиентом из VPN: папки
   и письма видны, вложения открываются.
4. Только чтение: удалить письмо, перетащить в другую папку, создать папку, пометить прочитанным —
   клиент должен получить отказ (или изменение пропадёт после переподключения). После этого
   бэкап ящика — без изменений числа писем.
5. Учётка ящика (`user@...` с паролем из БД) из VPN не пускает: в `journalctl -u dovecot` —
   `allow_nets check failed`. Учётка просмотра с адреса вне разрешённых сетей — тоже.

### Сервер для выгрузки (SFTP)

На другом сервере (подойдёт любой Linux с SSH):

```bash
sudo useradd -m -s /bin/bash mbcopy
sudo -u mbcopy mkdir -p ~mbcopy/.ssh && sudo -u mbcopy chmod 700 ~mbcopy/.ssh
# Публичный ключ — со страницы «Снимки» → «Создать SSH-ключ». Префикс ограничивает ключ одним SFTP:
echo 'restrict,command="/usr/lib/openssh/sftp-server" ssh-ed25519 AAAA… mail_backup@…' |
    sudo -u mbcopy tee -a ~mbcopy/.ssh/authorized_keys
```

В панели: «Добавить сервер» → адрес, порт, пользователь `mbcopy`, каталог `mail_backup`
(относительно домашнего) → «Проверить» (запоминается ключ сервера, его отпечаток виден
в таблице) → «Выгрузить сейчас». Первая выгрузка копирует всё, дальше — только новое.
По расписанию выгрузка идёт вместе с очисткой (по умолчанию в 05:00).

### Если этот сервер пропал

Снимки на удалённом сервере расшифровываются сохранённым паролем:

```bash
echo 'пароль-со-страницы-Снимки' > /root/restic.pass && chmod 600 /root/restic.pass
export RESTIC_REPOSITORY=sftp:mbcopy@backup.example.com:mail_backup RESTIC_PASSWORD_FILE=/root/restic.pass
restic snapshots --tag mailbox-3                      # снимки ящика №3
restic restore <id> --target /tmp/restore             # Maildir ящика: /tmp/restore/<путь>/Maildir
```

Дальше — новый сервер с `install.sh` и восстановление писем в ящик из распакованного Maildir
(например, через временную учётку Dovecot и imapsync).

## Если что-то пошло не так

Прислать:

- вывод установщика (последний экран);
- панель: `sudo journalctl -u mail-backup-web -n 50`;
- воркер: `sudo journalctl -u mail-backup-worker -n 50`;
- Dovecot: `sudo journalctl -u dovecot -n 50`;
- nginx: `sudo nginx -t` и `sudo journalctl -u nginx -n 30`;
- ошибка бэкапа: страница запуска в панели (лог внизу).
